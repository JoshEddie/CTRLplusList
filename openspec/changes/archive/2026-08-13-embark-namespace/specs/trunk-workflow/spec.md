## ADDED Requirements

### Requirement: The departure arc SHALL run as five prefixed skills with a stop at every boundary

The arc from a `CHARTED` issue to a landed implementation SHALL be carried by five skills sharing an `embark-` prefix, in this order: `/embark-start`, `/embark-design`, `/embark-qualify`, `/embark-write-tasks`, `/embark-apply`. There SHALL be no bare `/embark`.

- **Every boundary is a stop** — each member SHALL end its turn at its boundary, and each successor SHALL be resumable from repository state alone, with no reliance on the prior member's conversation. A member SHALL close by naming its successor.
- **One pause, not a stop** — `/embark-design` alone MAY pause mid-turn for the owner to check the grilling's conclusions; a pause continues the same conversation and needs no disk durability. Every other checkpoint in the arc is a stop.
- **Owner-invoked only** — every member SHALL carry `disable-model-invocation: true`, so no member fires on the model's own judgment. This is load-bearing for `/embark-apply`, which stamps `UNDER SAIL` and occupies the tree.
- **`/opsx:propose` and `/opsx:ff` SHALL NOT be on the arc** — a one-turn bundle offers the owner no checkpoint, and `/opsx:ff` additionally drops the planning boundary that keeps implementation behind `/embark-apply`. Artifacts SHALL be produced by `openspec new change` plus one `/opsx:continue` per artifact.
- **No member SHALL restate `/mattpocock-skills:grilling`'s own mechanics** — the one-question-at-a-time discipline and the owner-confirmation rule live in `/mattpocock-skills:grilling`'s skill file and SHALL be referenced, not duplicated.

#### Scenario: A dead chat does not lose the arc
- **WHEN** the session ends after any member completes and a fresh chat runs the named successor
- **THEN** the successor proceeds from the change directory alone — no member depends on a prior member's conversation surviving

#### Scenario: No member self-fires
- **WHEN** a session is working on unrelated matters and an arc member would be topically relevant
- **THEN** no member is invoked — every member is owner-invoked only, so the tree is never occupied on the model's judgment

#### Scenario: The bundle is never generated in one turn
- **WHEN** a change's planning artifacts are produced through the arc
- **THEN** each artifact is generated by its own `/opsx:continue` in the member that owns it, and neither `/opsx:propose` nor `/opsx:ff` is invoked

### Requirement: /embark-design SHALL run the grilling interview and write specs and design

`/embark-design` SHALL run on a change whose `proposal.md` exists. It SHALL run the `/mattpocock-skills:grilling` interview against the reviewed proposal, then generate `specs` and `design` in the same turn, then stop naming `/embark-qualify` and stating that it must run in a fresh chat.

- **The issue and its map are read first** — the skill SHALL read the issue the proposal records, the map that issue links, and any issue this one blocks, before the interview begins. The proposal is one reading of the issue, not a replacement for it. The map's Decisions so far are settled context, and the design SHALL unblock every dependent issue it read. The reads SHALL be bounded — the map's own body, not a walk of its sub-issues, and no sibling chunk beyond the ones this issue blocks.
- **Scope** — the issue is the scope. The interview SHALL ask only what this change needs settled to be right, and SHALL drop what it notices beside that.
- **Grilling after the proposal** — the interview SHALL aim at the proposal's stated Capabilities and Impact rather than first establishing what the change is. It SHALL cite the map's settled decisions rather than re-asking them, SHALL re-validate any unreviewed scouting decisions with the owner, and SHALL conclude only on the owner's explicit confirmation of shared understanding.
- **Pause, then durability** — after the interview concludes, the skill SHALL pause for the owner's check and SHALL run `/opsx:update` wherever the grilling moved a decision the proposal states, so the proposal is durable before specs are drafted.
- **Specs and design in one turn** — the grilling walks the design tree, which no artifact on disk yet holds: `proposal.md` has no section a design decision fits and `design.md` does not exist. Both SHALL therefore be written while the interview is still in the conversation.
- **Re-entry re-runs the grilling** — invoked with `proposal.md` present and no `specs/`, the skill SHALL run the interview again rather than skipping to specs; a second interview against an updated proposal is a supported outcome, cuttable short by the owner. Invoked with `specs/` present and no `design.md`, the interview SHALL still run — written specs are settled facts, cited and not relitigated — and `design` SHALL be the only artifact generated. The design tree the interview walks lives in no artifact on disk, so a run that skipped the interview would write design decisions nobody made.
- **Epic route-out** — the grilling MAY conclude the change is bigger than one OpenSpec change and, on the owner's confirmation, SHALL route out to `/map`'s chart phase in the same conversation, with prior answers carried per `map-workflow`'s re-validation sweep.

#### Scenario: The interview reads the issue the proposal names
- **WHEN** `/embark-design` runs on a change whose proposal records its issue
- **THEN** that issue and the map it links are read before the first question is asked — the interview is not aimed at the proposal alone

#### Scenario: A dependent chunk is read and unblocked
- **WHEN** the change's issue blocks another chunk on the map
- **THEN** that chunk is read before the interview, and the design unblocks it

#### Scenario: The map read stops at the map
- **WHEN** the map links sibling chunks this issue does not block
- **THEN** those chunks are not read — the map's own body is the whole of the map context

#### Scenario: Re-entry after specs still interviews
- **WHEN** `/embark-design` is invoked with `specs/` written and no `design.md`
- **THEN** the interview runs with the written specs cited as settled, and `design.md` is the only artifact generated — no delta spec is rewritten

#### Scenario: Grilling aims at a written proposal
- **WHEN** `/embark-design` runs on a change whose proposal states its Capabilities and Impact
- **THEN** the interview questions those stated positions rather than re-establishing what the change is

#### Scenario: A moved decision is made durable before specs
- **WHEN** the grilling changes a decision the proposal records
- **THEN** `/opsx:update` revises the proposal before `specs` is generated — specs are never drafted against a proposal the interview has already overtaken

#### Scenario: Specs and design are written in the interview's turn
- **WHEN** the grilling concludes on the owner's confirmation
- **THEN** `specs` and `design` are both generated in that same turn, and the skill stops afterward rather than continuing into acceptance or tasks

#### Scenario: Re-entry before specs re-runs the interview
- **WHEN** `/embark-design` is invoked a second time with `proposal.md` present and no `specs/` directory
- **THEN** the grilling runs again against the updated proposal — the owner may cut it short, but it is not skipped

#### Scenario: Design invoked before a proposal exists stops
- **WHEN** `/embark-design` is invoked on a change directory holding no `proposal.md`
- **THEN** it stops naming `/embark-start` — the interview has nothing grounded to aim at, and no artifact is generated

#### Scenario: Design grilling routes out an epic
- **WHEN** the grilling concludes mid-interview that the change is bigger than one OpenSpec change and the owner confirms
- **THEN** the session routes out to `/map`'s chart phase in the same conversation instead of drafting specs

### Requirement: /embark-qualify SHALL qualify the change in a fresh chat

A change qualifies when every user route it touches runs end to end on what its specs and design say. `/embark-qualify` SHALL generate `acceptance.md` in a conversation that did not author the documents it chains, and SHALL gate on the findings that generation surfaces — anything the draft cannot chain SHALL disqualify the change until repaired. Generating `acceptance.md` is not by itself a qualification; the artifact's own contract is `acceptance-artifact`'s, and what this member adds is the uncontaminated context and the gate.

- **Fresh chat SHALL be the first line** — a run carrying the grilling transcript knows things the documents do not state, so it completes routes the documents cannot support and reports no failure. Contaminated context does not degrade this run, it inverts its result. `/embark-design` SHALL name the requirement when it stops, and `/embark-qualify` SHALL state it before doing anything else.
- **Classification is this member's, not the artifact's** — generation surfaces every step it cannot source and stops there (`acceptance-artifact`). Naming what a surfaced step is, repairing it and gating on it SHALL live here, because they are what the member adds. The rules SHALL NOT be restated in the schema `acceptance` instruction.
- **Two failure types** — a **gap** is a step nothing backs, repaired by the specs gaining the scenario. A **contradiction** is design and specs disagreeing, repaired wherever the conflict actually sits, in either file. Only the first is a spec gap; the second is a coherence failure.
- **The three design.md cases** — `design.md` MAY name an **observable**; it SHALL NOT source a **behavior**:
  1. **Design names the observable** — a spec backs the step but names no surface, and design.md does. The row asserts design's observable, and this is not a finding: design supplied the handle, not the behavior.
  2. **Design asserts the behavior, and nothing else does** — a **gap**. The step SHALL NOT chain on design's authority; the scenario goes into the specs.
  3. **Design contradicts a spec** — a **contradiction**, disqualifying the change.
- **The verdict SHALL be reported before anything is repaired** — a repair adds a scenario to the binding contract, which is more durable than the proposal decision `/embark-design` already pauses for. The skill SHALL report the verdict, then **pause** on one question: repair the findings, or continue. This is a pause, not a stop; the conversation continues.
- **Continue is the owner's ruling, and its shape is theirs too** — on continue, whether a ruled step chains into its flow or stays out of it SHALL be the owner's call. The skill SHALL neither write an unsourced step on its own authority nor refuse one the owner has ruled.
- **Repair routes through `/opsx:update`** — a gap or contradiction SHALL be repaired by `/opsx:update`, never by editing an artifact directly, so the artifacts stay coherent with one another. The skill SHALL re-run afterwards.
- **Stop** — the skill SHALL stop after the run and any repair, naming `/embark-write-tasks` as its successor.

#### Scenario: A contaminated run is prevented by the boundary
- **WHEN** `/embark-design` stops after writing specs and design
- **THEN** it names `/embark-qualify` and states that it must run in a fresh chat — the qualification run never inherits the interview that produced the documents it is testing

#### Scenario: An unbacked step is a gap
- **WHEN** the run reaches a step no delta or existing scenario backs
- **THEN** the change is disqualified and `/opsx:update` adds the scenario to the specs before the flow chains through it

#### Scenario: Design disagreeing with a spec is a contradiction
- **WHEN** the run finds design.md asserting behavior the specs contradict
- **THEN** the change is disqualified as a coherence failure and `/opsx:update` repairs whichever file is wrong — the fix is not presumed to land in the specs

#### Scenario: A step whose behavior only design.md asserts is a gap
- **WHEN** the run reaches a step whose behavior nothing but `design.md` asserts
- **THEN** the change is disqualified as a gap and the scenario goes into the specs — the step does not chain on design's authority

#### Scenario: Design naming an observable for a backed step is not a finding
- **WHEN** a spec backs a step but names no observable, and `design.md` names the concrete surface
- **THEN** the row asserts that observable and the run reports no finding — design supplied the handle, not the behavior

#### Scenario: The verdict is reported before any repair
- **WHEN** the run surfaces a gap or a contradiction
- **THEN** the verdict is reported and the skill pauses on one question — repair or continue — rather than editing the specs and reporting a state that no longer holds

#### Scenario: Continue is the owner's ruling
- **WHEN** the owner answers the pause with continue
- **THEN** the skill neither writes an unsourced step on its own authority nor refuses one the owner has ruled — whether the step chains into its flow or stays out of it is the owner's call

#### Scenario: Repair never edits an artifact directly
- **WHEN** the owner answers the pause with repair
- **THEN** the repair runs through `/opsx:update`, not a hand edit of specs or design, and the run repeats afterwards

#### Scenario: The failure types are stated once, in the member
- **WHEN** the schema `acceptance` instruction and this member are compared
- **THEN** the failure types, the repair route and the verdict appear only here, and the instruction carries only the rule that an unsourceable step is surfaced

### Requirement: /embark-write-tasks SHALL write tasks and the review scaffold from disk

`/embark-write-tasks` SHALL generate `tasks` and the `review` scaffold, reading `specs` and `design` from the change directory and holding no conversation of its own.

The boundary above it is load-bearing: after `/embark-qualify` reports failures and `/opsx:update` repairs the specs, that chat still holds the pre-repair documents and the argument that changed them. Tasks written there can encode the argument rather than the settled contract. Because this member needs no conversation, the boundary costs nothing.

The skill SHALL stop after both artifacts exist, naming `/embark-apply` as its successor.

#### Scenario: Tasks are written against the repaired contract
- **WHEN** `/embark-qualify` repaired the specs and `/embark-write-tasks` runs afterward
- **THEN** tasks are derived from the specs and design as they stand on disk, not from the repair discussion

#### Scenario: The member asks nothing
- **WHEN** `/embark-write-tasks` runs
- **THEN** it generates `tasks` and the `review` scaffold without an interview — there is nothing for the owner to decide at this boundary

## MODIFIED Requirements

### Requirement: /embark-start SHALL gate on trunk preconditions and act only on CHARTED

The `/embark-start <issue#>` skill (née `/start-change`, then `/embark`) SHALL hard-stop unless the working copy is on `dev` and `dev` is up to date with its remote. It SHALL read the issue via `gh issue view` and board only when **both** conditions hold: the routing state is exactly `CHARTED`, **and** the issue has zero open blockers, verified via

```bash
gh api --paginate repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by \
  --jq '.[] | {number, state, title}'
```

Any other routing state SHALL stop, reporting the routing labels found; an open blocker SHALL stop with a message naming the blocking issue(s) (closed blockers do not gate); a failed blocker query SHALL stop loudly, never be read as "no blockers". The label check SHALL be an allowlist, not a routing table: it SHALL NOT enumerate the states it rejects, SHALL NOT route them to owning skills, and SHALL NOT delegate into the definition layer — an unrecognized or newly-added label therefore stops it, which is the correct outcome for a dispatcher whose only job is boarding cleared work. Lowercase labels SHALL NOT route.

Before creating anything, the skill SHALL run a terrain check: re-read the issue body and its linked map's Decisions so far against the current code and specs, surfacing anything that shifted since charting; a shifted map decision fires `/anchor`. The terrain check MAY conclude the issue is bigger than one OpenSpec change and, on the owner's confirmation, SHALL route out to `/map`'s chart phase in the same conversation, creating no change directory.

On proceed, the skill SHALL create the change directory and generate `proposal.md` — that artifact and no other — seeded from the issue body, citing the map's settled decisions rather than re-asking them. The proposal SHALL record the issue it was seeded from — the issue number when the skill was given a number, the URL when it was given a link — so every later member reads the in-scope issue from the change directory alone. It SHALL then stop, naming `/embark-design`. It SHALL NOT run the grilling interview, SHALL NOT generate specs, design, acceptance, tasks or review, and SHALL NOT create commits. Invoked on a change whose `proposal.md` already exists, it SHALL report that nothing remains for it and name `/embark-design`. It SHALL own no map mechanics of its own.

#### Scenario: Anything but CHARTED stops
- **WHEN** `/embark-start 42` runs against an issue whose routing state is anything other than `CHARTED` — including `OFF THE MAP`, `UNCHARTED`, `ADRIFT`, `UNDER SAIL`, `IN PORT`, `MAP`, or no routing label at all
- **THEN** the skill reports the routing labels it found and stops — no change directory is created, no work is delegated, and no state is re-charted

#### Scenario: An open blocker stops a CHARTED issue
- **WHEN** `/embark-start 42` runs against a `CHARTED` issue whose blocked-by query returns one or more blockers with state `open`
- **THEN** the skill stops with a message naming each open blocking issue — the label alone does not board

#### Scenario: Closed blockers do not gate
- **WHEN** `/embark-start 42` runs against a `CHARTED` issue whose blocked-by relationships all point at closed issues
- **THEN** boarding proceeds — sequencing history is not a gate

#### Scenario: An unknown label stops embark
- **WHEN** `/embark-start 42` runs against an issue carrying a routing label added to the machine after the skill was written
- **THEN** the skill stops rather than falling through to a catch-all route — the allowlist admits only `CHARTED`

#### Scenario: Terrain check catches drift before departure
- **WHEN** the terrain check finds a settled map decision contradicted by code landed since charting
- **THEN** `/anchor` fires on that decision before any change directory is created

#### Scenario: Chunk issue inherits map context
- **WHEN** `/embark-start` drafts the proposal for an issue whose body links a `MAP`-labeled index
- **THEN** the proposal reads the map's Decisions so far as settled context rather than restating them as open questions

#### Scenario: The proposal records the issue it came from
- **WHEN** `/embark-start 42` generates the proposal
- **THEN** `proposal.md` records issue 42 by number, or by URL when a link was given — a later member reads the in-scope issue from the change directory without being told it

#### Scenario: Boarding produces one artifact and stops
- **WHEN** `/embark-start 42` boards a cleared issue
- **THEN** the change directory is created, `proposal.md` is generated, and the skill stops naming `/embark-design` — no specs, design, acceptance, tasks or review artifact is written

#### Scenario: Propose grilling routes out an epic
- **WHEN** `/embark-start`'s terrain check concludes the issue is bigger than one OpenSpec change and the owner confirms
- **THEN** the session routes out to `/map`'s chart phase in the same conversation and no change directory is created

#### Scenario: Re-invocation after the proposal exists is a no-op
- **WHEN** `/embark-start 42` runs against an issue whose change already has `proposal.md`
- **THEN** it reports that nothing remains for it and names `/embark-design` — it does not re-board or regenerate the proposal

### Requirement: /embark-apply SHALL gate the apply stage and wrap opsx:apply

`/embark-apply` SHALL be the only route into occupying the tree.

- **Structural gate** — before the beacon is stamped it SHALL run `openspec validate --strict` on the change and hard-stop on failure. A malformed bundle — deltas missing without `skip_specs`, scenarios written with three hashtags instead of four, a Purpose too brief — is not worth occupying the tree for.
- **Gate** — it SHALL hard-stop when ANY issue is labeled `UNDER SAIL`, the board's single "the tree is occupied" beacon shared by both lanes, and SHALL NOT gate on tree-state heuristics.
- **Lanes** — its argument SHALL resolve to either an OpenSpec change (the charted lane: state the mid-voyage disciplines, delegate the task loop to `/opsx:apply`) or a `MUSTER`-labeled issue (the MUSTER lane, per its own requirement).
- **Stamp** — the same two acts in both lanes: add `UNDER SAIL`, and remove `CHARTED` if present. `MUSTER` is never removed.
- **Closing suggestion** — after the task loop, the skill SHALL emit a closing output line suggesting `/opsx:verify` in a fresh chat. It SHALL be a line of output, not a numbered step: a step invites the agent to decide whether to run it, and this call belongs to the owner.

#### Scenario: A malformed bundle does not occupy the tree
- **WHEN** `/embark-apply` runs on a change whose `openspec validate --strict` fails
- **THEN** the skill stops reporting the validation failure — no label is stamped and no implementation begins

#### Scenario: An under-sail voyage blocks a second voyage
- **WHEN** `/embark-apply` runs while any issue — charted or MUSTER — is labeled `UNDER SAIL`
- **THEN** the skill stops before touching anything, naming the occupying issue

#### Scenario: Implemented change under review does not block
- **WHEN** `/embark-apply` runs while the tree holds only a fully-implemented change awaiting review or landing plus the new change's artifacts, and no issue is labeled `UNDER SAIL`
- **THEN** the skill proceeds, adds `UNDER SAIL` to the new issue (removing `CHARTED`), and enters apply

#### Scenario: Under sail is the single occupied-tree beacon
- **WHEN** `/embark-apply` stamps `UNDER SAIL` — adding it, removing `CHARTED` if present
- **THEN** that label is the board's only "the tree is occupied" signal, and the skill's own gate reads it and nothing else

#### Scenario: Discipline defers discovery routing to the definition layer
- **WHEN** `/embark-apply` states the mid-voyage disciplines at the start of a voyage
- **THEN** it states that a discovery is never folded into the active change, that charting onto an open map runs through `/anchor` (whose charter move is owned by `anchor-and-run-aground`), and that a mirage stops work and fires `/run-aground` (owned by `anchor-and-run-aground`) — without mandating `OFF THE MAP` as the only route or restating the charter criteria

#### Scenario: Verify is suggested, never run
- **WHEN** the task loop completes
- **THEN** the skill's closing output suggests `/opsx:verify` in a fresh chat and does not invoke it — the decision stays with the owner

#### Scenario: Embark flips no label
- **WHEN** `/embark-start`, `/embark-design`, `/embark-qualify` or `/embark-write-tasks` produces its artifacts
- **THEN** no label is flipped — planning artifacts are tree state, authoritatively recorded by the change directory, and `/embark-apply` is the sole stamper on the execution side

### Requirement: Tests-only coverage chunks SHALL run the MUSTER lane with no OpenSpec change

- **Qualifies when** — a chunk SHALL run the MUSTER lane when every test it adds verifies a scenario already stated in an active spec (`openspec/specs/<capability>/spec.md`) and it changes zero production code: no new capability, no spec delta, nothing to seal.
- **Label** — such chunks SHALL carry the `MUSTER` routing label from birth (birth rule owned by `issue-cut.md`, per `map-workflow`), through the voyage, and into port. The marker never comes off, keeping a MUSTER voyage distinguishable from a charted one.
- **No change directory** — SHALL NOT get one, and SHALL NOT board `/embark-start`, whose allowlist admits only `CHARTED`. No member of the planning arc runs for a MUSTER chunk.
- **Plan** — SHALL live in the scout-cut ticket body: coverage rows plus deliberate skips.
- **Traceability** — SHALL flow test → spec via an in-file citation header naming the capability and scenario each test file verifies, never spec → test.
- **Review and landing** — `/muster-review`, then `/landfall`'s MUSTER branch.

#### Scenario: A MUSTER chunk never gets a change directory
- **WHEN** a `MUSTER`-labeled issue is picked up for implementation
- **THEN** work enters through `/embark-apply`'s MUSTER lane with the ticket body as the plan — no `openspec/changes/` directory is created and no planning-arc member is invoked

#### Scenario: Production code disqualifies the lane
- **WHEN** implementing a MUSTER chunk turns out to require any production-code change
- **THEN** the voyage stops back to the owner — the work no longer qualifies as tests-only and must route through the normal charted flow

### Requirement: /embark-apply SHALL run the MUSTER lane for MUSTER-labeled issues

When `/embark-apply`'s argument resolves to a `MUSTER`-labeled issue rather than an OpenSpec change, the skill SHALL:

- **Stamp** — add `UNDER SAIL`; `MUSTER` is never removed.
- **Plan** — treat the ticket body as the plan.
- **Staleness check** — grep every `#### Scenario:` heading the plan cites against active specs; on any missing heading, stop back to the owner as a stale plan.
- **Read `TESTING.md` in full** — before writing any test.
- **Citation header** — ensure every test file carries one, naming the capability and scenario it verifies.
- **Implement inline** — no `/opsx:apply` delegation, no task tracking.

The lane SHALL never commit and never stage unasked. The `openspec validate --strict` structural gate SHALL NOT apply to this lane: no change directory exists to validate.

#### Scenario: MUSTER lane enters inline implementation
- **WHEN** `/embark-apply 297` resolves issue 297 labeled `MUSTER` and every cited scenario heading exists in active specs
- **THEN** the issue gains `UNDER SAIL` alongside `MUSTER` and implementation proceeds inline from the ticket-body plan — no change directory, no `/opsx:apply`, and no validate step

#### Scenario: Stale plan stops the voyage
- **WHEN** the staleness grep finds a cited `#### Scenario:` heading absent from every active spec
- **THEN** the skill stops before writing any test and reports the missing heading to the owner — the plan is stale
